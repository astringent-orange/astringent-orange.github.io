VLN中的Harness

本文部分内容由AI生成

引言

假设让一个大语言模型修复代码仓库中的 Bug：它需要读取文件、搜索代码、修改实现、运行测试，再根据报错继续调整，最后确认问题是否解决。
模型可以负责理解问题和提出下一步操作，但文件访问、命令执行、结果回传、任务进度记录和失败恢复，都需要额外的程序来协调。这层围绕模型构建的运行与控制系统，通常称为 Agent Harness。

Harness 基础概念

定义与运行循环

Harness 可以理解为围绕 AI 模型构建的运行时支架。它连接模型、上下文、工具和执行环境，负责组织模型调用与工具执行，并管理任务状态和生命周期。

目前 Harness 没有完全统一的行业定义，不同论文和开发框架的模块边界可能不同。微软和 VS Code 的相关文档都将模型调用、工具协调、上下文管理、审批和会话状态视为 Harness 的重要职责。[1][2]

可以用下面的概念式理解一个 Agent 系统：

$$ \text{Agent System} \approx \text{Model} + \text{Harness} + \text{Tools} + \text{Environment} $$

  • Model：提供语言理解、视觉理解、知识、推理和决策能力。
  • Harness：管理模型调用、上下文、任务循环、工具执行、状态更新和权限。
  • Tools：提供外部能力，例如搜索文件、运行代码、查询数据库或控制机器人。
  • Environment：工具实际运行的环境，例如本地计算机、容器、云主机、仿真器或真实机器人。
    这是一种便于理解的划分，并非严格的行业标准。实际系统中，Harness、Tools 和 Environment 的边界可能有所重叠。

为什么需要 Harness

一次普通模型调用可以表示为：

$$ y = f_\theta(x) $$

模型根据输入 $x$ 生成输出 $y$。对于多步骤任务，系统还需要解析工具调用、检查参数和权限、执行工具、返回结果，并决定是否继续调用模型。

这些步骤通常由 Agent Loop（智能体循环）组织：

flowchart TD
    A[接收任务与当前状态] --> B[组织上下文]
    B --> C[调用模型]
    C --> D{模型输出类型}
    D -->|最终结果| G[检查完成条件并结束]
    D -->|工具调用| E[检查参数和权限]
    E --> F[执行工具]
    F --> H[收集反馈]
    H --> I[更新记忆与任务状态]
    I --> B

Harness 的核心组成

不同 Harness 的实现不完全相同，常见能力如下。

组成部分 主要职责 常见实现
Model Interface 接入模型、解析返回结果 API Client、模型路由、结构化输出
Agent Control Loop 管理任务循环和生命周期 Planning、Tool Calling、Retry、Stop
Tool Management 注册、分发和执行工具 Function Calling、MCP Client、API
Context Management 组织每轮模型需要的信息 Prompt、历史消息、检索、上下文压缩
Memory & State 保存任务进度和可复用信息 Working Memory、长期记忆、Checkpoint
Safety & Policy 限制危险操作和资源使用 权限、审批、沙箱、超时、预算
Observability 记录执行过程并定位问题 Logs、Traces、Metrics、评估记录

Model Interface 负责屏蔽不同模型 API 的差异，也可以根据任务选择不同模型。Agent Control Loop 管理模型调用、工具执行、重试和终止。Tool Management 处理工具注册、参数校验、调用分发和结果返回。Context Management 决定模型每轮能看到哪些信息。Memory & State 保存任务进度和历史经验。Safety & Policy 管理权限与风险。Observability 记录执行轨迹，便于调试和评估。

与相关概念的区别

概念 关注点 与 Harness 的关系
Agent 围绕目标持续采取行动的系统或行为模式 Harness 为 Agent 提供运行机制
Agent Framework 开发 Agent 的 SDK、抽象和组件库 可用于构建 Harness，也可能内置 Harness
Workflow 按预先定义的步骤组织任务 Harness 可以执行固定 Workflow
MCP 连接 AI 应用与外部工具、数据的协议 Harness 可以通过 MCP 接入工具
Tool 可被调用的具体能力 Harness 负责管理和调度
Skill 某类任务的可复用指导 Harness 可按需将 Skill 加入上下文
Memory 信息保存和检索机制 是 Harness 可以管理的子系统
Environment 工具实际运行的地方 Harness 将调用路由到执行环境

Workflow 通常沿预先定义的代码路径执行；Agent 可以根据中间结果动态选择下一步。[3] Harness 可以支持两种模式。MCP 解决工具和数据如何暴露给应用的问题，Harness 则管理何时调用、如何执行以及如何处理结果。[4]

Tool 通常是可执行函数，例如 search_files()；Skill 通常是说明适用条件、操作步骤和注意事项的指导文件。Skill 可以影响模型决策，但本身不一定执行动作。

Harness 与模型训练

Harness 和 Fine-tuning 是两个不同维度：Harness 关注模型如何运行和使用工具；Fine-tuning 关注是否利用任务数据更新模型参数。

组合 说明
Training-free + Harness 使用预训练模型，通过工具和运行时逻辑完成任务
Fine-tuned Model + Harness 微调模型，同时用 Harness 管理执行过程
Training-free + Workflow 使用预训练模型执行预定义流程
Fine-tuned End-to-End Policy 模型直接学习输入到动作的映射

论文中的 Training-free 需要结合具体定义理解。它可能只表示主 MLLM 没有针对当前任务微调；系统中的检测器、分割器或运动执行器仍可能是训练得到的模型。

Harness 的设计与开发

设计工具接口

每个 Tool 应有明确的名称、用途、输入输出 Schema 和错误类型。例如：

工具设计时应注意：

  • 参数含义清晰，返回结构稳定。
  • 只返回下一步决策需要的信息，避免结果过长。
  • 设置超时、错误码和必要的重试机制。
  • 对有副作用的操作增加权限检查和审批。
  • 对可能重复执行的操作考虑幂等性。
  • 在工具说明中写清适用范围和限制。

接口稳定后，可以替换工具的底层实现，而不必大幅修改上层决策逻辑。

上下文、记忆与状态管理

三者可以共享存储，但用途不同。

类型 保存内容 示例
Context 当前轮模型需要看到的信息 指令、相关文件片段、最近工具结果
Working Memory 当前任务的短期信息 当前目标、最近发现、待办事项
Long-term Memory 后续任务可能复用的信息 项目约定、历史经验
Task State 任务执行进度 已完成步骤、待处理步骤、当前状态
Execution Trace 实际发生的调用和结果 工具参数、返回值、错误、时间戳

Context 是模型当前输入的信息视图；Memory 负责保存和检索信息；State 表示任务当前处于什么阶段。

长任务不宜无限累积历史消息。常见做法是保留近期对话，将已完成步骤压缩成摘要，把重要决策和外部证据单独保存，并按当前子任务检索相关信息。证据最好带有来源和时间，避免使用过时信息。

Skill、Workflow 与动态规划

Workflow 适合步骤稳定的任务，例如读取数据、检查字段、清洗数据、生成统计结果并导出报告。Skill 适合封装可复用经验，例如代码审查步骤或故障排查指南。动态规划适合中间结果会改变后续操作的任务，例如测试失败后重新定位问题。

一个 Harness 可以同时使用固定 Workflow、按需加载的 Skill 和模型驱动的动态决策。

评估与 Harness Engineering

只看最终回答很难定位 Agent 的问题。建议记录模型调用、工具参数、工具结果、耗时、Token 消耗和异常，并分别评估三个层次：

层次 评估内容 指标示例
Model 是否理解任务、选择正确工具 工具选择准确率、参数正确率
Harness 是否正确管理任务和执行 状态恢复率、错误处理率、审批执行率
End-to-End 是否完成用户目标 成功率、总耗时、Token 成本、人工介入次数

失败原因也应分类，例如模型推理错误、工具接口错误、上下文遗漏、状态更新错误或环境执行失败。这样才能判断问题应该由模型还是 Harness 来解决。

Harness Engineering 指设计、维护和持续改进 Harness 的工程实践。OpenAI 的 Agent-first 开发实践强调：让 Agent 能读取项目文档、理解代码结构、运行测试、查询日志，并根据反馈迭代修改。[5] 常见做法包括维护清晰的项目文档、提供可检索的知识入口、把架构约束写入测试和 Lint，并将重复出现的问题沉淀为工具或自动化检查。

Harness 在 VLN 中的应用

从传统 VLN 到 Agentic VLN

传统端到端 VLN 通常学习视觉观测、语言指令和历史信息到导航动作的映射：

$$ a_t = \pi_\theta(o_t, l, h_t) $$

其中 $o_t$ 是当前观测，$l$ 是语言指令，$h_t$ 是历史信息，$a_t$ 是导航动作或 Waypoint。模型通过导航轨迹训练，学习指令理解和运动策略。

Agentic VLN 将导航组织成持续的决策循环：MLLM 理解任务、分析场景并选择操作；Harness 管理记忆、工具、任务状态和反馈；导航执行器将目标转换成实际运动。高层 MLLM 可以低频决定子目标，局部规划器和控制器则高频处理路径跟踪和避障。

HarnessVLN

论文：HarnessVLN: Unifying Training-Free Embodied Navigation through an Agent Harness


HarnessVLN 将感知、检索、目标定位、导航、恢复和终止组织在统一工具接口中，有三大创新点：

  • 分层事件记忆：Working Memory 保存当前观测和近期反馈；Progress Memory 记录子目标状态；Reflection Memory 保存碰撞、不可达、定位不一致和无进展等事件。
  • 时空图：记录地点、实体、空间关系、观测时间和失败信息，用于检索历史证据、回退和重新规划。
  • 工具与执行验证：通过 observe、retrieve_memory、ground_target、query_depth、navigate_to、backtrack 和 request_stop 等工具完成交互。

Harness 在执行前检查目标证据、几何可达性和子目标一致性。停止请求也需要经过验证，可以概括为：

$$ F_{\text{stop}} = F_{\text{semantic}} \land F_{\text{geometric}} \land F_{\text{progress}} $$

HarnessVLN 采用 Training-free 路线，不针对当前导航任务对主 MLLM 进行专门微调。系统仍使用预训练的 GroundingDINO、SAM 等感知模型，并结合 FMM 等几何规划方法；部分场景还会调用已有的学习型 NavDP 执行器。因此，Training-free 不代表系统中所有模块都未经训练。

SuperNav

论文：SuperNav: An Agentic Navigation System for Any Task in Any Scene


SuperNav 为预训练 MLLM 配置 Agent Harness，重点包括 Agent Loop、Navigation Skills、工具接口、任务进度管理和 Visual-Point Interface。

  • Navigation Skills：以 Markdown 形式的Skill文件组织探索、目标搜索、入口搜索、失败恢复和任务完成检查等能力。MLLM 根据任务按需读取 Skill，从而执行不同的操作。
  • Visual-Point Interface：模型不直接生成复杂的底层控制动作，而是转为在图像中指定目标点，形式可表示为：

$$ \operatorname{PointNav}(d,[u,v]) $$

其中 $d$ 表示观测视角，$u,v$ 表示归一化图像坐标。导航工具负责将图像点转换成实际目标并执行移动。

  • 运动执行后端：Geo-based Executor 使用深度、相机标定、位姿和导航网格进行几何规划；Learned Executor 使用训练得到的局部运动策略预测位移。

SuperNav 不对主 MLLM 进行导航专用微调，但 Learned Executor 本身仍是经过训练的运动模块。

两种方法的侧重点

维度 HarnessVLN SuperNav
主要关注 记忆、空间证据、执行验证 Skills、工具接口、任务泛化
记忆组织 分层事件记忆与时空图 任务进度和交互历史
导航接口 语义 Grounding、深度查询、导航工具 图像视角与 Visual Point
失败处理 失败记录、空间检索、回退和验证 Skill 指导重新搜索和恢复
运动执行 可替换 Navigation Executor Geo-based / Learned Executor

两者都采用 Harness 思路，但任务终止机制有所区别。HarnessVLN 对停止请求设置明确的证据检查；SuperNav 的终止工具主要记录 MLLM 对完成或受阻的判断，工具关闭会话本身不等于任务已被独立验证为成功。

Harness 与端到端模型的关系

Harness 是系统架构，Training-free 是训练策略，两者可以自由组合。

方案 高层 Planner 低层 Executor Harness 职责
Training-free Harness 预训练 MLLM 几何规划或已有策略 工具管理、记忆和任务控制
Fine-tuned Harness 微调 VLM / MLLM 几何或学习型策略 管理执行和反馈
Hybrid Harness 通用 MLLM 负责任务级推理 专用小模型负责 Waypoint 和局部运动 管理长程任务、记忆和恢复

HarnessVLN 的 R2R-CE、RxR-CE 对比表中，ABot-N0 和 HarnessVLN 的结果如下：

方法 模型/训练路线 R2R SR R2R SPL RxR SR RxR SPL
ABot-N0 4B，导航任务训练 66.4 63.9 69.3 60.0
HarnessVLN Training-free Harness 60.8 43.5 53.9 38.0

数据来自 HarnessVLN 论文的 R2R/RxR Val-Unseen 对比表。[6] 这组结果说明，通用 MLLM 的语义推理能力不会自动转化为高效运动能力。经过导航轨迹训练的专用模型可以学习更适合导航的动作分布；Harness 的记忆和验证机制有助于任务管理，但无法自动补足底层运动精度。SR 关注任务是否成功，SPL 还考虑路径效率，增加观察和回退可能改善成功率，也可能增加路径长度。

这不是严格的计算效率对比。若要比较系统成本，还需统计模型调用次数、Token、感知模型耗时、执行器耗时、总任务时间和部署成本。

对室内连续环境 VLN 的启发

在传统VLN模型中也存在一定的如对记忆进行管理，语义分割以及拓扑图等类似结构，但是harness框架将其规范化修改为可拓展性更强的方法，可以理解为VLN模型在工程上的落地实现。
一个可研究的方向是 Hybrid Harness-VLN：Harness 管理长程任务，小型导航模型处理局部运动。

flowchart TD
    A[语言指令与环境观测] --> B[High-level Harness]
    B --> C["MLLM：任务理解与子目标规划"]
    C --> D["记忆检索、进度管理、失败恢复"]
    D --> E[Fine-tuned Navigation Policy]
    E --> F[Waypoint / 局部运动目标]
    F --> G[Local Planner & Controller]
    G --> H[连续室内环境]
    H --> I["RGB-D、位姿、碰撞与执行反馈"]
    I --> B

可以重点关注长期空间记忆、动态子目标规划、失败恢复、Skill 学习、安全验证和 Agent Loop 效率。实验可比较 4B 端到端模型、Training-free MLLM + Harness、4B Navigation Policy + Harness。除 SR 和 SPL 外，还应报告任务完成时间、恢复成功率、平均决策次数、模型调用成本和跨场景泛化能力。
